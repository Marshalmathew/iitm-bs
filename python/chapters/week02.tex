\chapter{Control Flow \& Conditionals}

Programs must make robust decisions based on changing, stochastic data. In Python, \index{Control Flow}\textbf{Control Flow} governs the execution trajectory of a program through conditional evaluation. Unlike lower-level compiled languages that enforce branch logic through explicit block delimiters (such as curly braces \texttt{\{\}}) and rigid boolean types, Python pairs significant whitespace indentation with an expressive \textbf{truth-value testing protocol} and short-circuit boolean semantics. In modern data science and machine learning, conditional branching serves as the foundational mechanism behind rule-based systems, data cleaning pipelines, and recursive decision-tree algorithms.

\section{Mathematical \& Computational Foundations}

\subsection{Propositional Logic and Truth Tables}

\begin{definitionbox}{Boolean Logic and Connectives}
\index{Propositional Logic} \index{Truth Tables}
Let $P$ and $Q$ be propositional statements that evaluate to truth values in the set $\mathbb{B} = \{\text{True}, \text{False}\}$. Python provides three fundamental logical connectives:
\begin{enumerate}
    \item \textbf{Conjunction (\texttt{and}):} $P \land Q$ is \texttt{True} if and only if both $P$ and $Q$ are \texttt{True}.
    \item \textbf{Disjunction (\texttt{or}):} $P \lor Q$ is \texttt{True} if at least one of $P$ or $Q$ is \texttt{True}.
    \item \textbf{Negation (\texttt{not}):} $\neg P$ is \texttt{True} if $P$ is \texttt{False}, and \texttt{False} if $P$ is \texttt{True}.
\end{enumerate}
These operations follow \textbf{De Morgan's Laws}:
\begin{equation}
\neg(P \land Q) \iff (\neg P) \lor (\neg Q)
\end{equation}
\begin{equation}
\neg(P \lor Q) \iff (\neg P) \land (\neg Q)
\end{equation}
\end{definitionbox}

\subsection{The Python Truth-Value Testing Protocol}

In Python, an expression tested inside an \texttt{if} or \texttt{while} condition does not strictly require an instance of \texttt{bool}. Instead, any object can be tested for truth value.

\begin{theorembox}{Truthiness and Falsiness Hierarchy}
\index{Truthiness} \index{Falsiness}
By default, an object is considered \textbf{truthy} unless its class defines a \texttt{\_\_bool\_\_()} method that returns \texttt{False} or a \texttt{\_\_len\_\_()} method that returns \texttt{0}.
The following built-in objects are strictly evaluated as \textbf{falsy}:
\begin{itemize}
    \item \textbf{Constants:} \texttt{None} and \texttt{False}.
    \item \textbf{Numeric Zeros:} Integer \texttt{0}, float \texttt{0.0}, complex \texttt{0j}, \texttt{Decimal(0)}, \texttt{Fraction(0, 1)}.
    \item \textbf{Empty Sequences and Collections:} Empty string \texttt{""}, empty tuple \texttt{()}, empty list \texttt{[]}, empty dictionary \texttt{\{\}}, empty set \texttt{set()}, empty \texttt{range(0)}.
\end{itemize}
All other objects---including non-empty strings (\texttt{"0"}, \texttt{"False"}), non-empty collections (\texttt{[0]}, \texttt{\{False\}}), and non-zero numbers---are evaluated as \textbf{truthy}.
\end{theorembox}

\subsection{Short-Circuit Evaluation and Return Values}

\begin{theorembox}{Operational Semantics of Short-Circuit Evaluation}
\index{Short-Circuit Evaluation}
Python's logical operators \texttt{and} and \texttt{or} do not return explicit boolean flags; rather, they return the \textbf{actual operand value} that determined the outcome:
\begin{enumerate}
    \item \textbf{Expression \texttt{X and Y}:}
    Python evaluates \texttt{X}. If \texttt{X} is falsy, evaluation terminates immediately (short-circuits) and returns \texttt{X}. If \texttt{X} is truthy, Python evaluates and returns \texttt{Y}.
    \begin{equation}
    \text{\texttt{X and Y}} = \begin{cases} X & \text{if } \text{bool}(X) = \text{False} \\ Y & \text{if } \text{bool}(X) = \text{True} \end{cases}
    \end{equation}
    \item \textbf{Expression \texttt{X or Y}:}
    Python evaluates \texttt{X}. If \texttt{X} is truthy, evaluation terminates immediately and returns \texttt{X}. If \texttt{X} is falsy, Python evaluates and returns \texttt{Y}.
    \begin{equation}
    \text{\texttt{X or Y}} = \begin{cases} X & \text{if } \text{bool}(X) = \text{True} \\ Y & \text{if } \text{bool}(X) = \text{False} \end{cases}
    \end{equation}
\end{enumerate}
This ensures that expensive computations or potentially crashing operations (e.g., division by zero or index access) on the right-hand side are never executed if the left operand guarantees the result:
\begin{lstlisting}[language=Python]
# Division by zero is completely avoided:
if count != 0 and (total / count) > threshold:
    process_average()
\end{lstlisting}
\end{theorembox}

\subsection{Chained Comparison Invariant}

\begin{theorembox}{Equivalence of Chained Comparisons}
\index{Chained Comparisons}
In mathematics, writing $a < b \le c$ asserts that $b$ is strictly bounded between $a$ and $c$. In Python, comparison operators chain arbitrarily:
\begin{equation}
a \mathbin{\text{op}_1} b \mathbin{\text{op}_2} c \iff (a \mathbin{\text{op}_1} b) \land (b \mathbin{\text{op}_2} c)
\end{equation}
Crucially, the middle subexpression $b$ is \textbf{evaluated exactly once}. If $a \mathbin{\text{op}_1} b$ is \texttt{False}, $c$ is never evaluated at all.
\end{theorembox}

\section{Deep Intuition \& Conceptual Derivations}

\subsection{Conditional Expressions (The Ternary Operator)}
Python supports inline conditional expressions that yield values rather than controlling control blocks:
\begin{equation}
\text{\texttt{result = Expr\_True if Condition else Expr\_False}}
\end{equation}
Unlike C-style ternary operators (\texttt{cond ? expr1 : expr2}), Python places the condition between the expressions to reflect natural English readability. The expression lazily evaluates: if \texttt{Condition} is truthy, \texttt{Expr\_False} is never evaluated.

\subsection{Module Imports and the Namespace Architecture}
When expanding conditional logic with math routines or random sampling, we import Python standard modules:
\begin{itemize}
    \item \texttt{import math}: Loads module into memory, binds identifier \texttt{math} to the module object. Requires qualified access: \texttt{math.sqrt(x)}.
    \item \texttt{from math import sqrt, pi}: Imports specific attributes into the current namespace. Allows direct invocation: \texttt{sqrt(x)}.
    \item \texttt{import numpy as np}: Binds the module object to an alias, preventing namespace pollution while maintaining brevity.
\end{itemize}

\section{Explicit Gotchas \& Diagnostic Misconceptions}

\begin{trapbox}{Bitwise (\texttt{\&}, \texttt{|}) vs Logical (\texttt{and}, \texttt{or}) Precedence}
Using bitwise operators \texttt{\&} and \texttt{|} instead of logical operators in boolean conditionals is dangerous:
\begin{lstlisting}[language=Python]
x = 5
# Intention: check if x is between 0 and 10
if x > 0 & x < 10:  # BUG!
    print("In range")
\end{lstlisting}
Because bitwise \texttt{\&} has higher operator precedence than comparison \texttt{>}, Python parses this expression as:
\begin{equation*}
x > (0 \mathbin{\&} x) < 10 \implies 5 > 0 < 10 \implies (5 > 0) \land (0 < 10)
\end{equation*}
While it coincidentally evaluates to \texttt{True} here, if $x = 0$, $0 > (0 \& 0) < 10 \implies 0 > 0 < 10 \implies \text{False}$, but with complex types or arrays, this triggers severe type errors or logical corruptions! Always use \texttt{and} / \texttt{or} for scalar booleans.
\end{trapbox}

\begin{trapbox}{Short-Circuit Operand Masking with Non-Booleans}
Because \texttt{or} and \texttt{and} return operand objects rather than booleans, assigning fallback defaults can introduce silent bugs:
\begin{lstlisting}[language=Python]
# Fallback idiom: use default if input is empty
user_limit = input_val or 100
\end{lstlisting}
If \texttt{input\_val} is explicitly set to \texttt{0} (a legitimate non-negative threshold), Python treats \texttt{0} as falsy and silently overwrites it with \texttt{100}! Correct idiom: \texttt{user\_limit = input\_val if input\_val is not None else 100}.
\end{trapbox}

\begin{trapbox}{Float Equality in Branching Conditions}
Never test floating-point numbers for exact equality inside conditionals:
\begin{lstlisting}[language=Python]
total = 0.1 + 0.2
if total == 0.3:  # Evaluates to False!
    print("Match")
\end{lstlisting}
Because $0.1 + 0.2 = 0.30000000000000004$, strict equality fails. Always use tolerance-based comparisons:
\begin{lstlisting}[language=Python]
import math
if math.isclose(total, 0.3, rel_tol=1e-9):
    print("Match")  # Evaluates to True!
\end{lstlisting}
\end{trapbox}

\begin{trapbox}{Chained Comparison Misinterpretation}
Consider the expression: \texttt{3 > 2 == 1}.
Programmers familiar with left-to-right parenthesization might expect:
\begin{equation*}
(3 > 2) == 1 \implies \text{True} == 1 \implies \text{True}
\end{equation*}
In Python, this is a chained comparison, expanding to:
\begin{equation*}
(3 > 2) \land (2 == 1) \implies \text{True} \land \text{False} \implies \mathbf{False}
\end{equation*}
Never rely on mixed-operator chaining across inequalities and equalities without explicit parentheses.
\end{trapbox}

\section{Python / Scientific Computing Lab}

The following industrial script implements an anomaly-scoring and credit-risk decision engine utilizing short-circuit guards, tolerance comparisons, and chained conditional thresholds.

\begin{lstlisting}[language=Python]
import math

def evaluate_credit_application(applicant: dict) -> dict:
    """
    Evaluates credit risk and approval status using layered conditionals,
    short-circuit safeguards, and chained comparisons.
    """
    # Guard clause: applicant must provide valid records
    if not applicant or "income" not in applicant or "credit_score" not in applicant:
        return {"status": "REJECTED", "reason": "Incomplete documentation"}

    income = applicant["income"]
    score = applicant["credit_score"]
    dti = applicant.get("debt_to_income", 0.0)  # debt-to-income ratio

    # Guard clause: numerical validity
    if income <= 0 or not (300 <= score <= 850):
        return {"status": "REJECTED", "reason": "Invalid numerical parameters"}

    # Decision tree hierarchy
    if score >= 750 and dti < 0.35:
        tier = "Tier 1: Prime"
        base_rate = 0.055
    elif 650 <= score < 750 and dti < 0.45:
        tier = "Tier 2: Near Prime"
        base_rate = 0.085
    elif 580 <= score < 650 and dti < 0.50:
        tier = "Tier 3: Subprime"
        base_rate = 0.125
    else:
        return {"status": "REJECTED", "reason": "Credit profile exceeds risk parameters"}

    # High net-worth adjustment using ternary operator
    rate_discount = 0.005 if income >= 120000 else 0.0
    final_rate = max(0.02, base_rate - rate_discount)

    # Floating point precision check for rate ceiling
    if math.isclose(final_rate, 0.05, abs_tol=1e-5):
        rate_category = "Benchmark"
    else:
        rate_category = "Custom"

    return {
        "status": "APPROVED",
        "tier": tier,
        "interest_rate": round(final_rate, 4),
        "rate_category": rate_category
    }

# Unit tests
test_client = {"income": 135000, "credit_score": 780, "debt_to_income": 0.28}
decision = evaluate_credit_application(test_client)
print("Application Decision:", decision)
# Output: Application Decision: {'status': 'APPROVED', 'tier': 'Tier 1: Prime', 
#         'interest_rate': 0.05, 'rate_category': 'Benchmark'}
\end{lstlisting}
